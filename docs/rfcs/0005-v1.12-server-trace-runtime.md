# RFC 0005：v1.12 服务端追踪运行时

- 状态：Accepted
- 目标版本：v1.12
- 适用平台：Node.js 服务端、Web；保持 iOS 与 Android 帧兼容

## 背景

v1.10 引入 `dct-qim-v1` 隐形 locator，v1.11 增加批量分发、轻度缩放恢复、Web 协作式异步检测和 Content Credentials 适配器。生产文档已经建议把 Web 端长期密钥和批量分发放在可信服务端，但项目当前只有 C2PA 签名与验证示例，没有可以在 Node.js 中嵌入或检测 locator 的正式运行时。

这形成了一个明显断点：移动端和浏览器能够演示完整算法，真正需要集中管理密钥、批量分发、泄漏调查和审计记录的服务端却要自行重写图片解码、像素处理和 API 编排。

同时，Web robust detection 虽然会定期归还事件循环，但总 CPU 工作仍在主线程。高分辨率图片或多个并行检测任务仍可能影响交互；批量取消也只能阻止尚未开始的任务，不能终止已经进入检测器的单项。

## 目标

1. 提供不依赖 DOM、Canvas 或 React Native 的通用隐形水印运行时工厂。
2. 通过调用者提供的图片 codec 解码、编码，让 Node.js、边缘运行时或其他服务端适配器复用同一套像素算法。
3. 提供基于 Node.js 22 和 `sharp` 的独立 Trace Service 示例，覆盖嵌入、检测、记录查询与可选 Content Credentials。
4. Web 支持显式配置的专用 Worker，在 Worker 中执行像素检测并支持真正终止正在运行的任务。
5. 维持 v1.10/v1.11 帧格式、密钥规则、检测结果和原生实现兼容性。
6. 建立跨 Web、Node.js、iOS、Android 的黄金向量和可重复变换基准。

## 非目标

- 不把 `sharp`、C2PA Node 二进制、数据库驱动或 Web Worker bundler 加入核心包运行时依赖。
- 不在核心 SDK 中实现账户、鉴权、租户、计费、对象存储或生产数据库。
- 不允许 Trace Service 从普通 HTTP 请求接收水印主密钥或 C2PA 私钥。
- 不承诺抵抗任意旋转、透视、截图、打印拍照或生成式去水印。
- 不在本版本更改 `dct-qim-v1` 帧格式或声明标准 C2PA soft binding。
- 不自动创建 blob Worker；严格 CSP 环境必须能够从调用者控制的同源 URL 加载脚本。
- 不在 v1.12 发布第二个公共 npm 包。独立 package 先作为仓库内示例稳定 API 和部署边界。

## 通用 Trace Runtime

核心包新增纯 TypeScript 工厂：

```ts
interface InvisibleWatermarkDecodedImage {
  data: Uint8Array | Uint8ClampedArray;
  width: number;
  height: number;
}

interface InvisibleWatermarkCodec<Source, Output> {
  decode(
    source: Source,
    options: { maxSize: number }
  ): Promise<InvisibleWatermarkDecodedImage>;

  encode(
    image: InvisibleWatermarkDecodedImage,
    options: {
      format: 'jpeg' | 'png';
      quality: number;
      filename?: string;
    }
  ): Promise<Output>;
}

const runtime = createInvisibleWatermarkRuntime({
  codec,
  maxConcurrency: 4,
});

await runtime.embedInvisible({
  image: { src: inputBuffer },
  payload: 'asset-42',
  key,
  strength: 'robust',
  saveFormat: ImageFormat.png,
});

await runtime.detectInvisible({
  image: { src: suspectBuffer },
  key,
  strength: 'robust',
  search: 'robust',
});
```

运行时还提供与 Marker 一致的 `embedInvisibleMany()` 和 `detectInvisibleMany()`。结果同序、单项失败隔离、进度与取消语义复用共享批量执行器。

codec 负责输入格式、EXIF orientation、尺寸限制和最终编码；运行时只处理 RGBA 像素与既有算法。`decode()` 返回的像素必须是从左到右、从上到下的 RGBA，且方向已归一化。运行时在嵌入前复制像素，禁止修改 codec 共享或缓存的输入缓冲。

`maxSize` 默认 2048，并作为明确值传给 codec。codec 必须保持宽高比且不得放大原图。JPEG 输出默认质量 90，PNG 忽略有损质量语义。

核心包继续保持零生产依赖。Node.js 示例使用 `sharp` 实现 codec，但该实现不进入主 npm tarball。

## Node.js Trace Service

新增独立 `examples/trace-service` package：

- Node.js 22。
- `sharp` 解码 JPEG/PNG、归一化 EXIF orientation、限制最大尺寸并导出 RGBA。
- 使用通用 Trace Runtime 写入与检测 locator。
- 使用内置 `node:http`，不引入 Web 框架。
- 默认只监听 `127.0.0.1`。
- 请求体、像素数量、媒体类型和 base64 格式均有限制。
- 水印密钥从 `TRACE_WATERMARK_KEY` 或注入的 secret provider 读取，不出现在请求体、响应或日志中。
- locator 记录通过可注入 store 保存；示例内存 store 仅用于本地演示。
- 可注入 Content Credentials adapter；未配置时只执行 trace workflow。

### HTTP API

#### `POST /v1/traces/embed`

请求包含 JPEG/PNG、locator、可选公开 metadata、强度和输出格式。服务端使用自己的密钥嵌入，保存记录，并可选择在最终像素上追加 Content Credential。

响应包含输出图片、算法、locator、记录 ID 与可选 manifest ID。响应禁止回传密钥。

#### `POST /v1/traces/detect`

请求包含待检查图片、强度和搜索模式。响应包含认证后的检测结果，以及 locator 命中时由 store 返回的记录摘要。

#### `POST /v1/traces/verify`

在一次请求中执行 locator 检测、记录查询和可选 Content Credentials 验证，返回相互独立的 `trace`、`record` 和 `credentials` 字段。C2PA 验证失败不能被误报为 locator 检测失败，反之亦然。

服务不提供“列出全部记录”的端点，避免本地演示自然演变为可枚举的生产接口。

## Web Worker 检测

`DetectInvisibleWatermarkOptions` 新增 Web 专用配置：

```ts
interface InvisibleWatermarkWorkerOptions {
  /** Same-origin or explicitly allowed module/classic Worker script URL. */
  scriptUrl: string;
  /** Cancels and terminates the active Worker detection. */
  signal?: AbortSignal;
  /** Receives coarse lifecycle progress without pixel or key data. */
  onProgress?: (progress: {
    phase: 'queued' | 'detecting' | 'complete';
  }) => void;
}

interface DetectInvisibleWatermarkOptions {
  // existing fields...
  worker?: InvisibleWatermarkWorkerOptions;
}
```

Web Marker 仍在主线程加载图片并读取 Canvas 像素，因为该阶段受 DOM、CORS 和浏览器图片解码约束。若提供 `worker.scriptUrl`：

1. SDK 创建一次性专用 Worker。
2. 把新复制的 RGBA `ArrayBuffer` 作为 transferable 交给 Worker。
3. Worker 使用同步像素检测器，避免在独立线程里引入无意义的 `setTimeout()` 分片。
4. 成功、失败或取消后都终止 Worker 并清理监听器。
5. `AbortSignal` 在开始前取消时不创建 Worker；运行中取消时调用 `terminate()` 并以 `AbortError` 拒绝。

未提供 Worker 配置时继续使用 v1.11 的协作式异步检测。Worker 创建失败、脚本加载失败或协议不匹配时显式报错，不静默回退，以免调用者误以为任务已离开主线程。

发布包提供独立、无外部 import 的 worker artifact。调用者负责把它复制到同源静态资源目录并把 URL 传给 SDK；文档分别给出 Vite/Astro、Expo Web 和普通静态站点示例。这样不依赖某个 bundler 对 `new Worker(new URL(...))` 的转换规则，也兼容严格 CSP。

## Worker 协议

协议使用版本号，避免页面缓存旧 worker 后产生不可解释结果：

```ts
type WorkerRequest = {
  protocol: 1;
  id: string;
  type: 'detect';
  pixels: ArrayBuffer;
  width: number;
  height: number;
  options: {
    key: string;
    strength?: InvisibleWatermarkStrength;
    search?: InvisibleWatermarkSearch;
  };
};
```

响应只允许 `ready`、`result` 或 `error`。错误响应包含稳定 code 和非敏感 message，不包含 key、像素或堆栈。客户端忽略 ID 不匹配的消息并最终超时由调用者或 `AbortSignal` 控制。

## Content Credentials 组合

Trace Service 的顺序固定为：

1. codec 解码并归一化像素。
2. 写入 invisible locator。
3. 编码最终 JPEG/PNG。
4. 保存 locator 审计记录。
5. 若配置 Content Credentials adapter，对已经写入 locator 的文件签名。

检测与验证彼此独立报告。私有 assertion 继续只保存 `SHA-256(locator)`，不保存 locator 明文，也不声明 `c2pa.watermarked`。

## 可靠性基准

仓库新增可重复的 Node.js 基准脚本和固定素材清单，至少覆盖：

- PNG 直接输出。
- JPEG 90/75/60 重编码。
- 0.9、0.95、1.05、1.1 缩放。
- JPEG 75 后再轻度缩放。
- 小范围裁剪。
- 错误 key 与未嵌入图片。

CI 使用较小固定矩阵阻止回归；完整维护者基准生成 JSON 报告但不依赖 runner 的绝对耗时。v1.12 的发布门槛为：

- 当前 Web/iOS/Android 黄金向量全部保持兼容。
- Node 直接 PNG、JPEG 75 和四个缩放候选全部恢复。
- CI 负样本与错误 key 零误报。
- Worker 检测与主线程检测结果深度相等。
- Worker 取消会终止任务，并且不留下挂起 Promise 或事件监听器。
- 核心 npm tarball 不包含 `sharp`、C2PA runtime、示例数据库或测试素材。

旋转、透视、截图和打印拍照只记录实验数据，不作为 v1.12 成功标准。若数据证明可以在可接受误报与成本下恢复，再通过后续 RFC 扩展算法或搜索策略。

## 安全与隐私

- 服务端只嵌入随机 locator，不在图片中写入姓名、邮箱或订单详情。
- store 的 metadata、保留周期、访问控制和删除策略由部署者负责。
- 服务响应与日志不输出密钥、原始图片、C2PA 私钥或完整内部记录。
- 示例没有默认公网鉴权，因此文档必须明确要求放在应用自己的鉴权、速率限制和 TLS 之后。
- Worker 会接收图片像素与检测 key；它必须来自调用者信任的同源资源并受 CSP 约束。
- 任何远程 Worker URL 都可能读取 key 和像素，文档禁止把生产检测交给第三方 Worker。

## CI

- 根测试覆盖 runtime codec 合同、输入快照、批量顺序、取消和错误隔离。
- Worker 客户端使用 fake Worker 覆盖成功、协议错误、脚本错误、提前取消和运行中取消。
- 浏览器矩阵在 Chromium、Firefox、WebKit 中运行真实 worker artifact，并与主线程结果比较。
- Trace Service 独立执行 `npm ci`、类型检查、单测、`sharp` 模块加载和生产依赖审计。
- Node 22 与 Node 24 都运行 Trace Service smoke，发布工作流继续使用 Node 24。
- npm dry-run 检查示例与 `sharp` 不进入主包。

## 发布策略

上述能力统一在 v1.12.0 发布。`createInvisibleWatermarkRuntime()`、codec 合同和 Worker 配置作为稳定 API；`examples/trace-service` 仍为参考实现，不承诺托管服务 SLA。若后续需要发布独立 Node package，必须先有至少一个版本的示例 API 使用反馈，并通过新的 RFC 确认包名、版本联动和长期维护责任。
