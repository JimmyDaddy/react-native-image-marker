# RFC 0003：v1.10 隐形追踪水印 Beta

- 状态：Accepted
- 目标版本：v1.10
- 适用平台：iOS、Android、Web

## 背景

现有 API 解决的是可见文字、Logo 与多图层合成。版权追踪、按收件人分发、素材泄露定位和内容凭证恢复还需要一种不破坏画面的短标识：发布前把一个不透明资产 ID 写进最终像素，文件被再次保存后仍可检测并关联到服务端记录。

隐形水印不是加密、DRM 或不可移除的所有权证明。本 RFC 只定义可验证的数字传播能力，不使用“无法删除”“绝对安全”或“证明图片未修改”等表述。真实性与来源声明应由签名记录或 C2PA Content Credentials 提供；水印只负责恢复一个 locator。

## 目标

1. 在 iOS、Android 和 Web 上嵌入、检测同一种版本化水印格式。
2. 直接保存、PNG 往返和 JPEG 质量 60 以上重新编码后仍能恢复短 payload。
3. 提供置信度、误码率和算法版本，不把检测简化为不透明的布尔值。
4. 通过密钥派生的置换、抖动和认证标签降低伪造风险。
5. 与 v1.9 recipe/batch 组合，为每个输入嵌入不同追踪 ID。
6. 保持原有 `mark*` API、输出路径和 Web data URL 行为不变。

## 非目标

- 不承诺抵抗严重模糊、大面积遮挡、重绘、生成式修复或有针对性的去水印攻击。
- 不在首版承诺稳定通过截图、透视、打印后拍照等物理传播链路。
- 不把主密钥存入 SDK、浏览器 bundle 或示例代码。
- 不直接嵌入姓名、邮箱、订单信息等个人数据。
- 不在首版引入神经网络模型、远程验证服务或 C2PA 签名实现。
- 不允许任意长度消息；首版只承载短 locator。

## 公共 API

```ts
type InvisibleWatermarkStrength = 'subtle' | 'balanced' | 'robust';
type InvisibleWatermarkSearch = 'fast' | 'robust';

interface EmbedInvisibleWatermarkOptions {
  image: { src: any };
  payload: string;
  key: string;
  strength?: InvisibleWatermarkStrength;
  quality?: number;
  filename?: string;
  saveFormat?: ImageFormat;
  maxSize?: number;
}

interface DetectInvisibleWatermarkOptions {
  image: { src: any };
  key: string;
  strength?: InvisibleWatermarkStrength;
  search?: InvisibleWatermarkSearch;
  maxSize?: number;
}

interface InvisibleWatermarkDetectionResult {
  detected: boolean;
  payload?: string;
  confidence: number;
  bitErrorRate?: number;
  algorithm: 'dct-qim-v1';
}

Marker.embedInvisible(options): Promise<string>;
Marker.detectInvisible(options): Promise<InvisibleWatermarkDetectionResult>;
```

`embedInvisible()` 与现有 native API 一样返回缓存文件路径，Web 返回 data URL。`detectInvisible()` 不写文件。

`payload` 必须是 1 到 12 个 UTF-8 字节。推荐使用服务端生成的随机 locator 或压缩后的资产 ID。`key` 至少 16 个 UTF-8 字节；它只用于本地置换、抖动和认证，不应硬编码在公开客户端。

## 水印帧格式

v1 固定为 176 bit：

| 字段          |   长度 | 说明                  |
| ------------- | -----: | --------------------- |
| magic         | 16 bit | 固定 `IM`             |
| version       |  8 bit | 当前为 `1`            |
| payloadLength |  8 bit | 1 到 12               |
| payload       | 96 bit | UTF-8，未使用字节补零 |
| CRC-16/CCITT  | 16 bit | 检测传输错误          |
| auth tag      | 32 bit | HMAC-SHA256 截断值    |

32 bit 认证标签只用于减少误检和低成本伪造，不等同于完整数字签名。需要公开验证或长期真实性时，payload 应指向服务端签名记录。

## 嵌入算法

1. 将最终合成结果按 8×8 像素块处理，保留 alpha。
2. 从 RGB 计算亮度，只修改 DCT 中频系数差，不改 DC 分量。
3. 使用差分 QIM 将一个 frame bit 写入一对中频系数。
4. HMAC 派生的确定性置换决定 176 bit 在 16×11 block tile 中的位置。
5. HMAC 派生的 coefficient pair 和 dither 防止所有图片出现固定写入模式。
6. tile 在整张图中重复；裁剪保留足够内容时仍可能聚合出完整帧。
7. `subtle`、`balanced`、`robust` 只改变量化间隔，不改变帧格式。
8. 水印在所有可见图层合成完成后、JPEG/PNG 编码前写入。

检测器对每个 frame bit 汇总重复 block 的软判定，再验证 magic、版本、CRC 与 auth tag。`bitErrorRate` 是候选帧与各 block 硬判定之间的不一致比例；`confidence` 综合有效帧、重复次数、软判定余量和误码率并归一化到 `0...1`。

## 搜索模式

- `fast`：只检测原始 8×8 网格与零 tile 相位。用于 SDK 直接输出、PNG 和 JPEG 重编码，默认启用。
- `robust`：额外搜索 block 网格偏移与 tile 相位，尝试恢复有限裁剪；后续可增加小范围 block-size 搜索支持轻度缩放。

`robust` 是显式的高成本路径。Web 必须在文档中说明它会读取整张 Canvas 像素，并受跨域 Canvas 安全规则限制。

## 平台实现

### Web

- 使用现有 Canvas 加载、尺寸限制和编码逻辑。
- `getImageData()` 后运行 TypeScript 参考实现，再 `putImageData()`。
- 将 tainted canvas 的 `SecurityError` 转换成现有 CORS 指引。

### Android

- 使用 `Bitmap.getPixels()` / `setPixels()` 处理 ARGB_8888 数据。
- 通过 `javax.crypto.Mac` 计算 HMAC-SHA256。
- 复用现有串行任务限制、图片加载、原子写入和编码流程。

### iOS

- 将规范化后的 `UIImage` 转成 RGBA buffer，处理后重新创建 `CGImage`。
- 通过 CryptoKit 计算 HMAC-SHA256。
- 复用现有异步 limiter、图片加载与原子文件写入。

native bridge 传输动态 options；检测结果在原生层序列化成 JSON，再由 JavaScript wrapper 解析，以避开旧版 React Native codegen 对嵌套联合返回值的限制。

## 安全与隐私

1. 算法公开，安全性依赖密钥与服务端记录，不能依赖“别人不知道算法”。
2. Web 端调用者、浏览器扩展和页面脚本都可能读取 key；生产环境应传入短期 token 或在可信服务端嵌入。
3. payload 必须是随机 locator，SDK 文档禁止直接嵌入个人数据。
4. 检测到 payload 不证明图片未被修改，只说明当前像素中存在可验证标记。
5. 攻击者可以牺牲图片质量破坏标记；README 必须明确这一点。

## 校验与错误

- 图片缺失、payload 为空或超过 12 UTF-8 字节、key 少于 16 字节时在 JavaScript 层立即拒绝。
- native 端重复校验，防止绕过 wrapper。
- 小于 128×88 像素的图片无法容纳完整 frame，嵌入时拒绝。
- 未检测到、CRC 错误或 auth tag 错误不是异常，返回 `detected: false`。
- 不支持的算法版本、strength 或 search 值抛出参数错误。

## 测试与验收

### 确定性

- TypeScript、Kotlin、Swift 使用相同 frame、CRC、HMAC、置换和 coefficient pair 黄金向量。
- 相同 key/payload/像素输入的 frame 与 block 判定必须一致；最终编码字节不要求一致。

### 正确性

- 三端 embed 后立即 detect。
- 错误 key、无水印图片、被破坏的 CRC/auth tag 不得误报。
- Unicode 按 UTF-8 字节限制；边界 1/12/13 字节覆盖。
- alpha、PNG、JPEG、base64、maxSize 和安全 filename 不回归。

### 抗性矩阵

v1.10 发布门槛：

- PNG 往返：必须恢复。
- JPEG 质量 90、75、60：必须恢复。
- 亮度/对比度轻度变化：必须恢复。
- 裁剪后保留至少 70% 面积：`robust` 模式纳入 Beta 测试，不作为所有图片的绝对保证。
- 0.9× 到 1.1× 缩放：作为实验指标记录，不在 v1.10 稳定承诺中。

自动化浏览器门禁至少使用仓库中的六张真实图片夹具，要求全部嵌入/检测成功且未标记原图零误报；发布前基准集继续覆盖自然风景、人物、建筑、低纹理天空、暗部和高噪点六类图片。像素质量使用 SSIM/PSNR 与视觉 diff，`balanced` 参考实现的自动化 PSNR 下限为 40 dB，不能只凭示例图判断。

## 示例与文档

- Playground 增加“隐形追踪”独立模式：输入短 ID/key、选择强度、嵌入后立即检测。
- 示例默认 key 只用于演示，并明确禁止复制到生产环境。
- React Native 与 Expo 示例提供 embed → detect 闭环。
- 中英文文档增加威胁模型、服务端 locator 工作流和 CORS/性能说明。

## 发布策略

作为 v1.10.0 Beta API 发布，但不使用 prerelease 版本号。API 名称与 frame v1 固定；`robust` 搜索能力可以在不改变帧格式的情况下增强。若后续引入 StegaStamp/HiDDeN 类模型，应使用新的算法标识和可选模块，避免增加基础包的默认体积。
