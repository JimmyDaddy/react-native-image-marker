# 需求文档

## 介绍

本文档概述了将 react-native-image-marker 库从传统桥接架构升级到 React Native 新架构的需求。新架构包括 Fabric（新渲染器）和 TurboModules（新原生模块系统）。此次升级将确保更好的性能、类型安全性和未来兼容性，同时保持与现有 API 的向后兼容性。

## 术语表

- **新架构**: React Native 的现代架构，由 Fabric 渲染器和 TurboModules 组成
- **TurboModules**: 新的原生模块系统，提供更好的性能和类型安全性
- **Fabric**: 替代传统渲染器的新渲染系统
- **JSI**: JavaScript 接口，JavaScript 和原生代码之间的新通信层
- **Codegen**: 从 TypeScript/Flow 规范生成原生代码的工具
- **传统桥接**: 正在被替换的旧 React Native 桥接架构
- **图片水印库**: 正在升级的 react-native-image-marker 库
- **向后兼容性**: 确保现有用户代码无需更改即可继续工作

## 需求

### 需求 1: TurboModule 实现

**用户故事:** 作为使用新架构的 React Native 开发者，我希望图片水印库使用 TurboModules，以便我能够受益于改进的性能和类型安全性。

#### 验收标准

1. 当库在新架构应用中使用时，系统应自动加载 TurboModule 而不是传统桥接模块
2. 当调用 TurboModule 方法时，系统应提供具有适当 TypeScript 定义的类型安全接口
3. 当 TurboModule 初始化时，系统应向 JSI 注册所有原生方法以实现 JavaScript 到原生的直接通信
4. TurboModule 应实现传统桥接模块的所有现有功能
5. 当 TurboModule 操作完成时，系统应返回与传统实现相同接口的 Promise

### 需求 2: Fabric 渲染器兼容性

**用户故事:** 作为 React Native 开发者，我希望图片水印库与 Fabric 渲染器无缝协作，以便我可以在新架构应用中无问题地使用它。

#### 验收标准

1. 当库在启用 Fabric 的应用中处理图片时，系统应通过新的图片加载管道处理图片加载
2. 当执行图片操作时，系统应正确集成 Fabric 的线程模型
3. 库应保持与传统和 Fabric 图片源的兼容性
4. 当使用远程图片时，系统应与 Fabric 改进的图片缓存机制协作

### 需求 3: Codegen 集成

**用户故事:** 作为库维护者，我希望使用 Codegen 生成原生接口，以便我能够确保类型安全性并减少手动代码维护。

#### 验收标准

1. 系统应包含定义所有原生模块接口的 TypeScript 规范
2. 当构建库时，Codegen 应自动生成原生 iOS 和 Android 接口代码
3. 生成的接口应完全匹配现有的 API 表面
4. 当 TypeScript 定义更改时，原生接口应重新生成以保持一致性
5. Codegen 规范应包含所有方法签名、参数类型和返回类型

### 需求 4: iOS TurboModule 实现

**用户故事:** 作为 iOS 开发者，我希望库使用现代 iOS TurboModule API，以便我能够在 iOS 设备上受益于改进的性能。

#### 验收标准

1. iOS 实现应符合 TurboModule 协议
2. 当调用方法时，iOS TurboModule 应使用 JSI 与 JavaScript 直接通信
3. iOS 实现应保持所有现有的 Swift/Objective-C 功能
4. 当处理图片时，系统应使用与传统实现相同的 Core Graphics 和 UIKit API
5. iOS TurboModule 应正确处理异步操作和 Promise 解析

### 需求 5: Android TurboModule 实现

**用户故事:** 作为 Android 开发者，我希望库使用现代 Android TurboModule API，以便我能够在 Android 设备上受益于改进的性能。

#### 验收标准

1. Android 实现应扩展 TurboModule 基类
2. 当调用方法时，Android TurboModule 应使用 JSI 与 JavaScript 直接通信
3. Android 实现应保持所有现有的 Kotlin 功能
4. 当处理图片时，系统应使用与传统实现相同的 Android 图形 API
5. Android TurboModule 应正确处理异步操作和 Promise 解析

### 需求 6: 向后兼容性

**用户故事:** 作为使用传统架构的 React Native 开发者，我希望升级后的库继续工作而无需任何代码更改，以便我可以逐步升级。

#### 验收标准

1. 当库在传统架构应用中使用时，系统应自动回退到桥接实现
2. 当现有用户代码调用库方法时，API 应保持相同且无破坏性更改
3. 库应在运行时检测架构并选择适当的实现
4. 当在架构之间切换时，行为和返回值应保持一致
5. 库应保持相同的错误处理和 Promise 拒绝模式

### 需求 7: 构建系统集成

**用户故事:** 作为 React Native 开发者，我希望库与新旧构建系统无缝集成，以便无论我的项目设置如何都能使用它。

#### 验收标准

1. 当为新架构构建时，系统应在构建过程中包含 Codegen
2. 当为传统架构构建时，系统应跳过新架构特定的构建步骤
3. podspec 应根据 RCT_NEW_ARCH_ENABLED 标志有条件地包含新架构依赖项
4. Android build.gradle 应根据 newArchEnabled 标志有条件地编译新架构代码
5. 当安装库时，构建系统应自动配置正确的架构支持

### 需求 8: 性能优化

**用户故事:** 作为 React Native 开发者，我希望新架构实现提供比传统版本更好的性能，以便我的应用运行更高效。

#### 验收标准

1. 当使用 TurboModules 时，系统应减少与桥接相比的 JavaScript 到原生通信开销
2. 当处理大图片时，新实现应显示可测量的性能改进
3. TurboModule 应最小化图片操作的数据序列化开销
4. 当执行多个操作时，系统应在适当的地方受益于 JSI 的同步能力
5. 新架构实现应保持或改善与传统版本相比的内存使用

### 需求 9: 类型安全和开发者体验

**用户故事:** 作为 TypeScript 开发者，我希望库为新架构提供全面的类型定义，以便我能够在编译时捕获错误。

#### 验收标准

1. 库应为所有 TurboModule 方法提供完整的 TypeScript 定义
2. 当在 TypeScript 项目中使用库时，编译器应验证所有参数类型和返回类型
3. 类型定义应包含图片选项和配置的适当泛型类型
4. 当使用 IDE 自动完成时，系统应提供准确的方法签名和文档
5. TypeScript 定义应从与原生代码相同的 Codegen 规范生成

### 需求 10: Expo 兼容性

**用户故事:** 作为 Expo 开发者，我希望升级后的库能够在 Expo 项目中正常工作，包括开发构建和生产构建，以便我可以在 Expo 生态系统中使用图片水印功能。

#### 验收标准

1. 当库在 Expo 开发客户端中使用时，系统应正确检测并使用适当的架构实现
2. 当使用 Expo 预构建（prebuild）时，系统应正确配置新架构支持
3. 库应包含适当的 Expo 配置插件以支持新架构设置
4. 当在 EAS Build 中构建时，系统应支持新架构和传统架构配置
5. 当使用 Expo SDK 时，库应与 Expo 的图片处理和文件系统 API 兼容

### 需求 11: 测试和验证

**用户故事:** 作为库维护者，我希望对两种架构进行全面测试，以便我能够确保升级不会引入回归。

#### 验收标准

1. 测试套件应包含传统和新架构实现的测试
2. 当运行测试时，系统应验证两种架构产生相同的结果
3. 测试应涵盖所有现有功能，包括文本水印、图片水印和各种选项
4. 当运行性能测试时，新架构应展示相对于传统实现的改进
5. CI 系统应针对两种架构配置测试库
